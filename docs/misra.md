# MISRA C++:2023 — what the firmware holds, and its deviations

The owner wants the firmware held to as much of MISRA C++:2023 as the project can reach, step by step. This page is the register: what is claimed, which gate holds each claim, and every known departure with its reason. It is not a compliance statement. No certified MISRA C++:2023 checker runs on this tree (they are all commercial: Cppcheck Premium, Helix QAC, Parasoft, Polyspace, PVS-Studio, LDRA), so a rule is listed as held only where a free gate checks it or where the code was read against the rule and the reading is written here.

## Scope

- **Own code**: everything under `firmware/src`. The rules apply to it.
- **Adopted code** (MISRA Compliance:2020's term): ESP-IDF, FreeRTOS, the C and C++ libraries, and the fake ESP-IDF of the host tests (`firmware/test/native/harness`). They are not required to comply; where they affect a claim about our code, this page says how.
- **Tests and host tools** (`firmware/test/native`, `host/`, `scripts/`) are outside the scope.

## Held, by the gates and by reading

- **6.7.2, global variables.** One, and it is not a program variable: `RMTMEM` (`firmware/src/status_led.cpp`), the RMT's symbol RAM, declared `extern "C" volatile` for the address the ESP32-S3's linker script gives it (`esp32s3.peripherals.ld`, `PROVIDE ( RMTMEM = 0x60016800 )`), a peripheral's memory the LED's blanker writes word by word (D7 for its name). clang-tidy's `cppcoreguidelines-avoid-non-const-global-variables` does not report it, an `extern "C"` declaration, so this sentence is what records it. Every object of the firmware's own has static storage inside a function, which keeps it out of 6.7.2 and puts it under 6.7.1 instead, a deviation of its own (D9): the five objects of the instrument are `constinit` statics of `app_main()` (`firmware/src/main.cpp`), and the TRACE ring a static of it that is not `constinit` (D9: no compiler evaluates its million elements as a constant expression, and an array of integers needs no guard), all reached only through the references `app_main()` hands out; the state of six modules (`flash_log`, `heap_monitor`, `i2c_bus`, `startup_memory`, `uart0`, `watchdog`) is a `constinit` static of each module's `state()` function, reached only through it; and the relay bank's reset record is a static of `relay::detail::resetRecord()` (D11). Constants at namespace scope are `constexpr`, or `const` objects (`kChannelNames`, an array of constant pointers to constant strings).
- **0.1.2, the value a function returns.** Every call's result is used or cast to `void` (FW-02, 2026-11-22): `bugprone-unused-return-value` with `CheckedFunctions` `.*` and `AllowCastToVoid` finds none left, in either leg. The 24 it found were the 11 `memcpy` and `memmove` calls below, 12 atomic read-modify-writes (`fetch_add`, `fetch_sub`, `fetch_or`) whose previous value no counter or flag set needs, and the ROM's `esp_rom_printf()` in `app_main()`'s fallback (gone in FW-26: the fallback writes through the ROM's `esp_rom_output_putc()`, which returns nothing); the casts are listed under D5.
- **21.2.2, the string handling functions of `<cstring>`.** No `memcpy` and no `memmove` (FW-02): of the eleven calls, eight became `std::copy_n` and `std::copy` (each a forward copy, the destination before the source where they overlap, which `std::copy` allows), and the other three, the calibration blob's reinterpretations of the bytes NVS returned, `std::bit_cast`, so no raw byte copy is left; from FW-16 the blob is a record of the flash log, read and written through `std::bit_cast` both ways and judged after a `std::copy_n` of its 80 bytes (`calibration.cpp`), and NVS's older layout is no longer read. `tests/firmware/test_static_analysis_gate.py` holds the sources to it. No `str*` function either (FW-22, 2026-11-23): names and patterns are carried as `std::string_view` (the command table's patterns, the profiles', the relays' and the error queue's names, every keyword list a handler matches), compared with `==`, `starts_with()` and `ends_with()`, their lengths from `size()`; numbers are read with `std::from_chars`; the 13 `strlen()`, the four `strncmp()` and the two `strcmp()` are gone, and no source includes `<cstring>`. `scripts/misra_rules.py` fails a call of any string handling function of `<cstring>`, `<cstdlib>`, `<cwchar>` and `<cinttypes>` by name, and an `#include` of `<cstring>`, `<string.h>`, `<cwchar>` or `<wchar.h>`, in any source of `firmware/src` ("Held by `scripts/misra_rules.py`" below; a planted call of each kind fails it). The headline also names `<cinttypes>`, which no source includes since FW-26: its `PRI*` format macros went with the formats (21.10.1 and 30.0.1 below).
- **0.2.4, functions with limited visibility used** (FW-20), and further: no function of the firmware's own, whatever its visibility, that no translation unit of the image references (the AST census, "The gates"), but the six test seams `scripts/ast_census.py` names, public functions the host tests call (`heap::disarm()` and `heap::attachCensus()`, which reset and re-ring the heap monitor between cases, `i2c_bus::clockHz()` and `i2c_bus::clearBus()`, which read back the bus's clock and run its recovery without a staged fault, from FW-22 the overload of `scpi::Parameters::choice()` over an array of C strings, which the parser's host tests were written against while the image's handlers keep their keywords as views and call the `std::span` overload, and, while 0.18.0 is built, `pinmap_store::save()`, which FW-03 lands with its record log and FW-05 calls from `SYSTem:PINS:APPLy`, taking its entry out, as FW-04 took out `load()`'s when the boot called it). Its first run reported eight (FW-20): five dead functions, deleted (`Sampler::pace()`; `channelFromName()` and `profileFromName()`, names the console resolves through its own tables; the one-argument `flash_log::mount()`, whose second argument the tests now give; and `calmath::pointsAgree()` with the two-point combination only it used, `agreementPpm()`, `combinedMicroOhm()` and `kRangeAgreementPpm`, which the host judges, `kleidos-meter calibrate` and the configuration's `range_split_max_ppm`, never the instrument), the two I2C functions now named as seams, and a function template, which the census now reads with its specializations.
- **6.9.2, no standard integer type's name** (FW-23, 2026-11-23). Members, constants, parameters and loop counters are `std::int32_t`, `std::uint32_t`, `std::uint64_t` or `std::size_t`: the 69 names the firmware's own code spelled outside a format (the interrupt router's cores and lines, the I2C master's port, core and command index, the parser's base, exponent and decimals, SHA-256's and the CRC's counters, the 128-bit division's bit, the console's self-test word and report fields, the relay bank's reserved pins and pad level) are gone. Where an ESP-IDF function takes or returns `int` (`esp_cpu_get_core_id()`, `gpio_get_level()`, `esp_cpu_intr_get_desc()`, the I2C and timer groups' low-level calls, `std::from_chars`'s base), the fixed-width value meets it by an implicit conversion between two 32-bit types of one signedness, which `-Wconversion` passes on both legs; no cast names `int` for it. The 49 that printf's formats needed (a `%d`, `%u`, `%*` or `%llu` reads `int`, `unsigned` or `unsigned long long` and no fixed-width type, so the casts in a printf-family call's arguments and the `int` count a `snprintf` returned kept them; D2's `d2.integer_names`, a count that only fell) went with the formats in FW-26, and none is left. `scripts/misra_register.py` reads every name from the sources (comments and literals removed, an alias declaration exempt as the rule exempts it) and fails any (`tests/firmware/test_misra_register.py`, with a planted name of each kind, a cast in a call's arguments among them).
- **7.11.2, no array decays to a pointer** (FW-26, 2026-11-23). No array of the firmware's own reaches a function or a constructor as a pointer: clang-tidy's `cppcoreguidelines-pro-bounds-array-to-pointer-decay` finds none in either leg and is suppressed nowhere, and the AST census counts `d3.decays` at 0, a ratchet ("The counts"). How the 132 that were left after FW-25 went, and the string literals counted apart, is D3's text.
- **Held by `scripts/misra_rules.py` (FW-21, "The gates")**: each rule below finds nothing in the image, a planted case of each fails it and its compliant twin passes (`tests/firmware/test_misra_rules.py`).

  - **7.0.3, no character's numerical value.** No conversion between a character type (`char` and the wide character types) and any other type, written or implicit, and so no arithmetic or ordering on a character (`c - '0'`, `c >= 'A'`), no character as a condition, no `static_cast<unsigned char>( c )` and no `static_cast<char>( byte )` (FW-22). ### D1. Allocation by adopted code: ESP-IDF before `app_main()` (21.6.1, adopted code)

### D3. C arrays (11.3.1, advisory)

### D11. The relay bank's reset record (4.1.1; 6.7.1 as D9)

`relay::detail::resetRecord()` (`firmware/src/relay.cpp`) returns a static `ResetRecord` placed with `RTC_NOINIT_ATTR` in RTC slow memory, which ESP-IDF's startup neither zeroes nor initializes, so that the coils energized when a reset came survive it and `ROUTe:STATe?` can say which relays the reset released (`released_by_reset=`, 0.16.0). The language zero-initializes every object of static storage before anything else runs; the attribute suspends that, which is a departure from the standard (4.1.1) and the reason the object has no initializer (one would be dropped without a word). The program reads, at every boot, a value it did not write in this run: on a power-on the memory holds noise, after any other reset what the previous run left. It is judged before it is used: `Bank::begin()` reads it only after a reset other than a power-on (`esp_reset_reason()`), takes it only when `recordWhole()` finds the magic word and the energized mask's complement beside it, and otherwise reports that no relay was released; it then overwrites the record whole before any relay is driven. In the abstract machine the object is zero-initialized and is set before it is read, so whether a checker would report the read under 11.6.2 (Mandatory, which MISRA Compliance:2020 lets no deviation cover) is to confirm against the owner's copy; what this page records is the attribute and the judged read. The record is also one of D9's static locals.

### D12. What 7.0.5's reading passes, to confirm against the owner's copy (7.0.5)

The gate ("Held") reads 7.0.5 as clang writes the conversions, and finds nothing in the image. Two things it passes, and one it does not read, are recorded here, because MathWorks' page lists no exception and does not say how its checker reads them; each is to confirm against the owner's copy of the standard:

- **A narrow unsigned operand that meets a wider unsigned one** (`flags & kMask` with `flags` a `std::uint8_t` and `kMask` a `std::uint32_t`). The language promotes the narrow operand to `int` first and then converts it to the unsigned type; clang writes the two steps as one conversion, unsigned to unsigned, and the gate reads no change of signedness. The value never passes through a negative `int`. This is the shape FW-23's `std::uint32_t` masks give every flag test and field read on a register value, `d12.widened_operands` in "The counts" (held by `tests/firmware/test_misra_rules.py`); a reading that counts the intermediate promotion would report each, and the remedy would be an explicit `static_cast<std::uint32_t>` on each narrow operand, or the narrow members widened at their declaration.
- **An integer literal is an operand like any other.** A literal of type `int` that meets an unsigned operand is reported and was suffixed (318 of them), although its value is never negative; if the rule's text exempts a non-negative constant expression, those suffixes are harmless and stay.
- **Not read:** an enumeration's promotion (its underlying type is not looked up), and a conversion inside a macro's expansion, which for ESP-IDF's and FreeRTOS's macros is adopted code (`RMT_LL_MAX_LOOP_COUNT_PER_BATCH`, `U0TXD_GPIO_NUM` and the other macros the sources compare are cast where they are used).

### D13. A callback's context cast from `void*` (8.2.6, required)

ESP-IDF's IPC call (`esp_ipc_call_blocking()`), its interrupt handlers (`intr_handler_t`, which the firmware's own router keeps for its table, `interrupt.h`) and FreeRTOS's task entry (`TaskFunction_t`) each take a function of `void ( void* )` and hand it back the pointer the caller registered with it. The callee casts that pointer back to the object it was given, which 8.2.6 forbids: a `void*` cast to a pointer type. The signatures are ESP-IDF's and FreeRTOS's, not ours to choose (as D7's names are not), and each callback is registered with exactly one type of object, in the same file, so the cast restores the type the pointer had. Replacing the pointer with a static accessor would not fit every site: `Ina228Driver::makeCall()` serves a request on the caller's stack, a different one each call, and the host tests build more than one `Sampler`. `scripts/misra_rules.py` counts every such cast (`d13.void_pointer_casts` under "The counts") and `tests/firmware/test_misra_rules.py` holds the casts it finds to these rows, file for file; a cast from an integer or an enumeration is a finding ("Held").

## The claim on the device: the bench session

The host session proves the firmware's own code against the harness's fakes, and the reachability gate what the image can call; the claim itself, `allocs_since_main=0 frees_since_main=0` for every operation, is proven on the instrument. Its run of record is the release's ("The run of record", below); a change that can move a count runs it on its own image before it is merged. The procedure, on the meter with a DUT drawing through the shunt, with the bench lock held (`docs/testing.md`):

1. `host/.venv/bin/python -m pytest -q -W error tests/bench --run-bench --meter-port "$KLEIDOS_METER_PORT" --bench-lock <lock> --bench-long --bench-record <file> --bench-session-record <file>`. ### What FW-18 took off

Fifteen allocations, 37,868 bytes, by configuration first and by a wrap or an own driver where no option exists (the census build of FW-17's commit, read on the meter on 2026-11-23, against FW-18's):

- **PSRAM in the heap** (3: its region record, 36 B, and the 32 KiB internal DMA reserve with its record, 32,768 and 36 B). `CONFIG_SPIRAM_USE_MEMMAP` maps PSRAM without registering it as a heap; the TRACE ring, PSRAM's one user, is placed at link time in `.ext_ram.bss`, which ESP-IDF zeroes at boot whatever the access method (`esp_psram_bss_init()`). On the meter (2026-11-23, against FW-17's image `1103c514a1c75d83`): `largest_internal` 237,556 to 270,324 bytes (+32,768, the reserve), `min_free_internal` 300,304 to 337,084 (+36,780: the reserve was taken out of the heap and then added back as a region of its own, so the boot's low-water mark sat 32 KiB lower), `free_internal` 332,323 to 337,108 (+4,785: the reserve was counted as free before, though only internal and DMA requests could have it), and `free_spiram` 4,192,124 to 0.
- **PSA's initialization** (5: two mutexes of 8 and 84 B each and the key slots' 1,408 B). Nothing in the image uses PSA, mbedTLS's startup hook calls `psa_crypto_init()` regardless, and no option leaves the hook out; the image is linked with `-Wl,--wrap=psa_crypto_init` onto `__wrap_psa_crypto_init()` (`firmware/src/startup_memory.h`), which answers `PSA_SUCCESS` and initializes nothing, and PSA's code leaves the image with its only caller. `scripts/check_heap_objects.py --elf` fails an image that links a `psa_` or `mbedtls_` function.
- **The idle tasks' memory** (4: two stacks of 1,596 B and two control blocks of 100 B). ESP-IDF's `vApplicationGetIdleTaskMemory()` takes them from the heap and has no option; `-Wl,--wrap=vApplicationGetIdleTaskMemory` hands FreeRTOS two static slots of the same size in internal RAM instead (`startup_memory.h`).
- **The brownout interrupt** (3: `rtc_isr_register()`'s record, 20 B, and the allocator's handle and descriptor, 8 and 16 B). ESP-IDF armed the detector with an interrupt because the promptless `CONFIG_SPI_FLASH_BROWNOUT_RESET` selects one, to reset an XMC flash chip; the meter's flash is a BoyaMicro part (manufacturer 0x68). `CONFIG_ESP_BROWNOUT_DET=n` leaves ESP-IDF's handling out and `firmware/src/brownout.h` arms the detector as ESP-IDF does without the interrupt, at the same level, right after `app_main()` releases the relays, with nothing allocated.
- **Not needed: VFS and mbedTLS's hardware options.** The VFS's two allocations (`esp_vfs_register_fs_common()`, 63 B) and mbedTLS's RSA DS lock (`esp_rsa_ds_conn_lock()`, 84 B) were in FW-07's census and left with FW-16's component list (the vfs component is out of the build, which `tests/firmware/test_meter_sdkconfig_reaches_the_build.py` holds, and `sdkconfig.defaults` turns its I/O off should it return); FW-17's census held neither, so no mbedTLS option was changed.
